DEPLOYMENT STEPS
============================================

STEP 1: PRE-MIGRATION CHECK (CRITICAL)
---------------------------------------
Before running migration, check for duplicate attendance records:

1. Open Supabase SQL Editor
2. Run this query:

   SELECT user_id, date, COUNT(*) as duplicate_count
   FROM attendance 
   GROUP BY user_id, date 
   HAVING COUNT(*) > 1;

3. If query returns rows (duplicates exist):
   - Document the duplicates
   - Run cleanup script (in MIGRATION_SECURITY_PHASE2.sql comments)
   - Verify duplicates are gone
   - Proceed to Step 2

4. If query returns 0 rows:
   - Proceed directly to Step 2

STEP 2: RUN DATABASE MIGRATION
-------------------------------
1. Open Supabase SQL Editor
2. Copy entire contents of MIGRATION_SECURITY_PHASE2.sql
3. Paste into SQL Editor
4. Click "Run"
5. Verify success messages
6. Run verification queries (commented in migration file)

Expected Results:
- attendance table has new columns: device_id, user_agent, ip_address, request_id
- UNIQUE constraint added: unique_user_date
- New table created: rate_limits
- New table created: audit_logs
- New function created: check_rate_limit()
- All indexes created successfully

STEP 3: TEST DATABASE LAYER
----------------------------
1. Test rate limit function:
   SELECT * FROM check_rate_limit('test-user', 'test-endpoint', 5, 10);
   
   Expected: Returns (true, 4, <timestamp>)

2. Test duplicate constraint:
   Try inserting duplicate attendance via SQL
   
   Expected: Error 23505 (unique violation)

3. Test audit logs:
   INSERT INTO audit_logs (admin_id, action_type, target_type, ip_address)
   VALUES ('<admin-uuid>', 'test', 'test', '127.0.0.1');
   
   Expected: Success

STEP 4: DEPLOY BACKEND CODE
----------------------------
1. Commit all changes to git
2. Push to repository
3. Deploy to Vercel (or your hosting platform)
4. Wait for deployment to complete
5. Check deployment logs for errors

STEP 5: TEST BACKEND SERVICES
------------------------------
1. Test Rate Limiting:
   - Try logging in 6 times with wrong password
   - Expected: 6th attempt should be blocked with rate limit message
   
2. Test Attendance Rate Limiting:
   - Try marking attendance 6 times rapidly
   - Expected: Should be blocked after 5 attempts
   
3. Test Device Tracking:
   - Mark attendance once
   - Check attendance table in Supabase
   - Expected: device_id, user_agent, ip_address should be populated

4. Test Duplicate Prevention:
   - Mark attendance once (should succeed)
   - Try marking attendance again immediately
   - Expected: Should fail with "Attendance already marked" error

STEP 6: MONITOR PRODUCTION
---------------------------
Monitor these metrics for first 24 hours:

1. Rate Limits Table Size:
   SELECT COUNT(*) FROM rate_limits;
   Expected: Should stay under 10,000 rows (cleanup working)

2. Rate Limit Violations:
   SELECT endpoint, COUNT(*) 
   FROM rate_limits 
   WHERE request_count >= 5 
   GROUP BY endpoint;
   Expected: Low numbers (< 10 per endpoint)

3. Duplicate Attempts:
   Check application logs for "Attendance already marked" errors
   Expected: Very few (< 5 per day)

4. Device Tracking:
   SELECT COUNT(DISTINCT device_id) FROM attendance;
   Expected: Should grow as employees use system

ROLLBACK PROCEDURE (IF NEEDED)
============================================

If issues arise, rollback in reverse order:

ROLLBACK STEP 1: Revert Backend Code
-------------------------------------
1. Git revert to previous commit
2. Redeploy to Vercel
3. Verify old code is running

ROLLBACK STEP 2: Remove Database Changes
-----------------------------------------
Run these SQL commands in order:

-- Drop function
DROP FUNCTION IF EXISTS check_rate_limit(TEXT, TEXT, INTEGER, INTEGER);

-- Drop tables
DROP TABLE IF EXISTS audit_logs;
DROP TABLE IF EXISTS rate_limits;

-- Remove constraint
ALTER TABLE attendance DROP CONSTRAINT IF EXISTS unique_user_date;

-- Remove columns
ALTER TABLE attendance 
DROP COLUMN IF EXISTS device_id,
DROP COLUMN IF EXISTS user_agent,
DROP COLUMN IF EXISTS ip_address,
DROP COLUMN IF EXISTS request_id;

-- Drop indexes
DROP INDEX IF EXISTS idx_attendance_device;
DROP INDEX IF EXISTS idx_attendance_request;
DROP INDEX IF EXISTS idx_attendance_ip;
